# Glances v5 — the Python API

**Date:** 2026-09-26
**Branch:** `develop-v5`
**Group:** v4 feature parity backlog
(`docs/architecture/glances-v5-architecture-decisions.md` §10, row "Python
API": *decided by the maintainer, 2026-09-26: port to v5, design first*)
**Blocks:** `--fetch` (its Jinja templates receive this API as `gl`).

---

## 1. Scope

v4 ships a small Python API: `from glances import api; gl = api.GlancesAPI()`.
Users read stats from a script or a notebook with it, and `--fetch` renders
its templates against it. v5 has no equivalent. This spec designs the v5 API.

Four decisions were taken with the maintainer on 2026-09-26, before this
document was written:

| # | Question | Decision |
|---|---|---|
| 1 | How does the API collect? | **On demand by default, continuous as an option**: `GlancesAPI()` updates a plugin when it is read, like v4; `GlancesAPI(background=True)` runs the v5 scheduler. |
| 2 | What does `gl.cpu` return? | **A read-only view**, not the plugin object. It keeps the v4 surface that is actually used, and adds the schema, the levels and the history. |
| 3 | Import path during the v4/v5 coexistence | **`glances.api_v5`**, renamed to `glances.api` at the `develop-v5 → develop` merge, like `main_v5`. |
| 4 | How `docs/api/python.rst` is generated | **A `make docs` target**, no CLI option (`--api-doc` now means Swagger). |

Out of scope: `--fetch` itself (next chantier, §8), remote access to another
Glances (that is the REST API, or Phase 3's remote client), and writing
anything to the host (the API is read-only, like the REST API minus its two
process-pin routes).

## 2. What v4 has

`glances/api.py`, about 120 lines:

- **Construction.** `GlancesAPI(config=None, args=None)` parses v4's CLI
  arguments when none are given (`GlancesMain().get_args()`). It builds a
  full `GlancesStats` and updates every plugin once, so that rates can be
  computed on the first read.
- **Access.** `gl.<plugin>` goes through `__getattr__`. It updates that one
  plugin, and its dependencies (`processlist` needs `processcount`), then
  returns **the v4 plugin object itself**. The result is cached for 2
  seconds (`weak_lru_cache(ttl=2.0)`, or `args.time`).
- **What users do with the returned object** (docs, notebook, tests,
  `--fetch` templates):
  - `gl.cpu['total']` and `gl.cpu.get('total')`;
  - `gl.network.keys()`, then `gl.network['eth0']`, which is a collection
    item keyed by its primary key (`list_to_dict`);
  - `gl.cpu.limits`;
  - `repr(gl.cpu)`, which prints the dict.
- **Helpers:**
  - `gl.plugins()`;
  - `gl.auto_unit(n)`;
  - `gl.bar(percent, size=18, bar_char='■', empty_char='□')`;
  - `gl.top_process(limit=3, sorted_by='cpu_percent')`, which excludes
    Glances itself;
  - `gl.__version__`, which holds the major version.

**Consumers:**

- `glances/outputs/glances_stdout_fetch.py` and the two shipped templates;
- `glances.ipynb`;
- `tests/test_api.py`;
- `docs/api/python.rst`, generated by v4's `--api-doc` through
  `glances_stdout_api_doc.py`;
- README and README-pypi.

**Defects that should not be carried over.**

1. **Plugin internals are exposed.** Returning the plugin object hands the
   user `update()`, `reset()`, `set_stats()` and every private attribute. A
   script can mutate what every later read sees.
2. **Parsing `sys.argv` on import.** `GlancesAPI()` with no arguments runs
   v4's argument parser against the *caller's* command line. A script run
   as `python myscript.py --foo` fails with a Glances usage error.
   `tests/test_api.py` has to patch `sys.argv` for this reason.
3. **The cache sits on `__getattr__` with `maxsize=1`.** Reading `gl.cpu`
   and then `gl.mem` evicts `cpu`, so alternating reads update on every
   access and the TTL never applies. The TTL is also frozen at 2 s: the
   decorator reads the class attribute when the class is defined, so the
   `self.ttl = args.time` in `__init__` never reaches it.
4. **`top_process` compares whole arguments.** `'glances' not in cmdline`
   tests whether an argument *equals* "glances". It hides `python -m
   glances`, but not `/usr/bin/glances` or `glances-v5`, the usual ways to
   start it.

## 3. What v5 has to work with

- The plugins are **async** (`await plugin.update()`), and publish to a
  `StatsStoreV5` that anyone can read without a lock.
- `main_v5.discover_plugins(store, config)` builds every enabled plugin.
  `attach_history()` gives the plugins the history store.
  `AsyncScheduler.run_forever()` updates the plugins continuously and feeds
  `GlancesAlerts`.
- The per-plugin read paths already exist:
  - `get_api_payload()` (data plus `_levels`) and `get_export()` (data only);
  - `get_limits()`;
  - `fields_description`;
  - `get_history()`.
- `mcp_adapter_v5.McpPluginView` is already a v4-shaped facade over one v5
  plugin, used by the MCP server.
- `processcount` drives the process engine that `processlist` and
  `programlist` read (`processlist/model_v5.py:27`). This is the same
  coupling as v4's `plugin_dependencies_tree`.
- Three plugins start background resources and have a `stop()`:
  `containers`, `mpp` and `ports`.

## 4. The API, as a user sees it

```python
>>> from glances import api_v5 as api          # `from glances import api` after the merge
>>> gl = api.GlancesAPI()                       # on demand; reads glances.conf like glances-v5 does
>>> gl.plugins()
['alert', 'amps', 'cloud', 'containers', 'core', 'cpu', ...]
>>> gl.cpu["total"]
7.7
>>> gl.cpu.get("steal", 0.0)
0.0
>>> gl.network.keys()
['eth0', 'lo']
>>> gl.network["eth0"]["bytes_recv"]          # a rate, B/s (v4: bytes_recv_rate_per_sec)
3472.0
>>> gl.mem.limits
{'percent': {'careful': 50.0, 'warning': 70.0, 'critical': 90.0}}
>>> gl.mem.levels                              # new: the level each watched field is at
{'percent': {'level': 'ok', 'prominent': True}}
>>> gl.mem.fields["percent"]["unit"]           # new: the schema (/api/5/mem/info)
'percent'
>>> gl.auto_unit(gl.mem["used"])
'6.07G'
>>> gl.bar(gl.cpu["total"])
'■□□□□□□□□□□□□□□□□□'
>>> gl.top_process(limit=3)
[{'pid': 104, 'name': 'claude', 'cpu_percent': 3.0, ...}, ...]
>>> gl.close()                                 # or: with api.GlancesAPI() as gl: ...

>>> with api.GlancesAPI(background=True) as gl:    # the scheduler runs in a thread
...     time.sleep(60)
...     gl.cpu.history(nb=30)                  # new: /api/5/cpu/history, same shape
...     gl.alerts()                            # new: /api/5/alert, same v5 schema
{'timestamps': [...], 'series': {'system': [...], 'user': [...]}}
```

## 5. Design

### 5.1 D1 — one private event loop, in a thread, in both modes

v5's plugins are coroutines. The API cannot call `asyncio.run()` in the
caller's thread, because a Jupyter notebook already runs an event loop there,
and `asyncio.run` refuses to start inside one. So `GlancesAPI` starts **its
own event loop in a daemon thread**, and every call from the user's thread
is handed over with `asyncio.run_coroutine_threadsafe(...).result()`. This
works the same from a script, from a notebook, and from inside someone
else's asyncio application.

Both modes share this loop:

- **On demand**: the loop only runs the update the caller is waiting for.
  It is idle, at zero CPU, between reads.
- **Background**: the loop runs `AsyncScheduler.run_forever()`, and reads go
  straight to the store, which needs no lock.

`close()` stops the scheduler if it runs, calls each plugin's `stop()` (for
the background resources of `containers`, `mpp` and `ports`), then stops the
loop and joins the thread. `GlancesAPI` is a context manager. A `weakref`
finaliser calls `close()` if the user forgets, so the three plugins'
background resources are never leaked.

### 5.2 D2 — on demand: per-plugin TTL, dependencies first (maintainer decision 1)

- **Construction.** It updates every enabled plugin once, as v4 does, so the
  first read already has rates. That costs one full cycle: 56 ms measured
  on the reference host for a second cycle, most of it in `processcount`
  and `system`.
- **Reading `gl.<name>`.** If that plugin's last update is older than the
  TTL, it is updated first; otherwise the store's payload is served. The
  TTL is `[global] refresh`, 2 s by default, which is what v4 meant with
  its `args.time` fallback. The TTL is **per plugin** and actually read
  from the config, which fixes defect 3.
- **Dependencies are declared, not hard-coded.** A plugin class gets an
  optional `DEPENDS_ON: ClassVar[tuple[str, ...]] = ()`. `processlist` and
  `programlist` declare `("processcount",)`. The API updates the
  dependencies first, under the same TTL. The scheduler does not use the
  attribute: it only documents a coupling that is already there
  (`processlist/model_v5.py:27`), and gives the API something to read
  rather than a list of its own.
- **Concurrency.** Two threads reading `gl.cpu` at the same moment trigger a
  single update: the per-plugin update runs under an `asyncio.Lock` on the
  API's loop.

### 5.3 D3 — background: the real v5 pipeline, minus what has side effects (maintainer decision 1)

`GlancesAPI(background=True)` assembles what `glances-v5` assembles in TUI
mode: the plugins, `attach_history()`, `GlancesAlerts`, and an
`AsyncScheduler` running on the API's loop. The history and the alerts
therefore fill up as they do in Glances itself.

Two things are **left out on purpose**, because an API object inside
someone's script must not act on the host by surprise:

- **No alert actions.** `GlancesAlerts` is built without actions, so the
  `[<plugin>] <field>_<level>_action` commands in `glances.conf` never run
  from the API. Alerts are recorded, never dispatched.
- **No exporters.** Nothing in `[export]` is started. Exporting is Glances'
  job, not a library's.

In on-demand mode, the history store is attached too, so `.history()`
returns what the reads recorded, with irregular timestamps. Alerts are fed
after each on-demand update as well. The spec documents that alert
durations then only mean something at the rate the caller reads.

### 5.4 D4 — `gl.<plugin>` is a `PluginView`, a read-only snapshot (maintainer decision 2)

```python
class PluginView(Mapping):        # collections.abc.Mapping: [], get, keys, items, values, len, in
    name: str
    raw: dict | list              # the export payload (v4 get_raw()), a copy
    fields: dict                  # fields_description (/api/5/<plugin>/info)
    limits: dict                  # get_limits() (v4 `.limits`)
    levels: dict                  # `_levels` (new)
    def history(self, nb=0, field=None, item=None) -> dict   # get_history() (new)
    def __repr__(self) -> str     # the dict, pretty-printed, as v4 prints it
```

- **A snapshot.** A view holds the payload as it was when `gl.cpu` was read.
  `v = gl.cpu; v["user"] + v["system"]` therefore adds two numbers from the
  same cycle, which v4's live plugin object did not guarantee. Reading
  `gl.cpu` again gives a fresh view.
- **Collections** map the **primary-key value** to the item, as v4's
  `list_to_dict` does: `gl.network["eth0"]`, `gl.processlist[1234]`,
  `gl.fs["/home"]`. Scalar plugins map the field to its value.
- **Read-only.** The view and the dicts it returns are copies. Mutating them
  changes nothing Glances or a later read sees, which fixes defect 1.
- **The data** is `get_export()`: no `_levels` in the items (they are
  `.levels`), and no field declared `exportable: False`. That is the same
  projection exporters get, and it is issue #3211's rule.
- **Shared with MCP.** `McpPluginView` already wraps one plugin for the MCP
  server. The read logic (payload, limits, history) moves into `PluginView`;
  `McpPluginView` keeps only its v4-shaped method names (`get_raw`,
  `get_raw_history`, `get_limits`) on top. That leaves one facade to
  maintain.
- **Errors.** An unknown plugin raises `AttributeError`, as in v4. A plugin
  disabled in `glances.conf` also raises `AttributeError`, with a message
  that names the config key. v4 returns the disabled plugin, whose stats
  stay empty, which reads as "nothing to report".

### 5.5 D5 — construction reads glances.conf, never `sys.argv` (fixes defect 2)

```python
GlancesAPI(config_path=None, background=False, plugins=None)
```

- `config_path` points to an extra `glances.conf`, layered as `-C` does.
  Without it, the v5 search path applies: system file, then XDG file, then
  `GLANCES_<SECTION>__<KEY>` environment overlays.
- `plugins` restricts the build to a list of plugin names. A notebook that
  only needs `cpu` and `mem` then pays neither for the process engine nor
  for `containers`. `processlist` without `processcount` pulls it in
  through `DEPENDS_ON`.
- **No `args` parameter and no `sys.argv` parsing.** v5's plugins read their
  configuration, not an argparse namespace. The only CLI-shaped inputs that
  mattered to v4's API (`-C`, `-t`) map to `config_path` and
  `[global] refresh`.

### 5.6 D6 — helpers: v4's three, unchanged in name and signature

- `gl.plugins()` lists the plugins that were built.
- `gl.auto_unit(number, low_precision=False, min_symbol='K', none_symbol='-')`
  and `gl.bar(value, size=18, bar_char='■', empty_char='□', pre_char='', post_char='')`
  keep v4's names and signatures, so v4 scripts and templates keep working.
- `gl.top_process(limit=3, sorted_by='cpu_percent', sorted_by_secondary='memory_percent')`
  still excludes Glances' own process, as in v4. It matches on the PID
  instead of on the command line, which fixes defect 4.
- `gl.alerts()` is new. It returns `GlancesAlerts.get_history()`, the list
  `/api/5/alert` serves.
- `gl.__version__` holds the major version, `"5"`, as v4 stored `"4"`.

The look-and-feel helpers that `--fetch` needs (the coloured quicklook bar,
titles) are **not** API methods. They are presentation, and belong to the
fetch renderer, which will hand its templates a second object next to `gl`
(§8).

### 5.7 D7 — documentation generated by `make docs` (maintainer decision 4)

`glances/api_v5_doc.py` writes `docs/api/python.rst`. It is run by the
`make docs` target, through `python -m glances.api_v5_doc`, and replaces
v4's `--api-doc > docs/api/python.rst` line. It produces:

- the usage section, from `GlancesAPI`'s and `PluginView`'s docstrings;
- one section per plugin: its fields, units and descriptions from
  `fields_description`, and **one real example**, taken from an on-demand
  read on the machine that builds the docs, as v4 does.

No user-facing CLI option is added.

## 6. Divergences from v4, recorded (release notes)

| v4 | v5 | Why |
|---|---|---|
| `from glances import api` | `from glances import api_v5` until the merge, then `api` again | Coexistence (decision 3). |
| `gl.cpu` is the plugin object | A read-only `PluginView` snapshot | Defect 1; decision 2. |
| `GlancesAPI(config, args)`, parses `sys.argv` | `GlancesAPI(config_path, background, plugins)` | Defect 2. |
| v4 field names (`bytes_recv_rate_per_sec`, `_gauge`, `key`) | v5 field names (`bytes_recv` is the rate; see each plugin's `.fields`) | v5's schema. The same break as `/api/5`. |
| A disabled plugin reads as empty | `AttributeError` naming the config key | Clearer. |
| `top_process` hides a process with an argument equal to "glances" | Hides Glances' own PID | Defect 4. |
| Nothing | `.fields`, `.levels`, `.history()`, `gl.alerts()`, `background=True`, `plugins=` | New in v5. |

## 7. Test strategy

- **The loop.** `GlancesAPI` works from a thread that already runs an event
  loop, the Jupyter case: a test builds and reads it inside a running
  `asyncio` loop. `close()` joins the thread and calls `stop()` on the three
  plugins that have one. The finaliser closes a forgotten instance.
- **On demand.**
  - Two reads within the TTL trigger one update; a read after it triggers a
    second.
  - Alternating `cpu` and `mem` reads respect each TTL (defect 3).
  - `processlist` updates `processcount` first.
  - Concurrent reads from two threads trigger one update.
- **Background.** The scheduler runs and the store refreshes with no read.
  `.history()` fills up. **A configured alert action never runs**, checked
  with a spy action. No exporter starts, even with `[export]` configured.
- **PluginView.**
  - It is a Mapping.
  - Collections are keyed by the primary key: `/home` for fs, an int PID
    for processlist.
  - Mutating a view does not reach the store.
  - The data equals `get_export()`, and `.limits`, `.fields`, `.levels` and
    `.history()` equal their REST counterparts for the same cycle.
- **Construction.**
  - `sys.argv` is ignored: a test sets a hostile `sys.argv`.
  - `config_path` layers over the defaults.
  - `plugins=` builds only those plugins, plus their `DEPENDS_ON`.
  - A disabled plugin raises `AttributeError` with the key named.
- **Helpers.** `auto_unit` and `bar` match v4's output for the same inputs.
  `top_process` excludes the test process's own PID.
- **MCP.** The existing adapter tests pass unchanged on top of the shared
  `PluginView`.
- **Docs.** The generator produces an RST that `docutils` parses without
  warnings, with one section per built plugin.
- **The v4 suite.** `tests/test_api.py` is ported as `test_api_v5.py`, the
  same assertions on v5 names, which proves the parity claim of D4 and D6.

## 8. What comes after

- **`--fetch`** renders against `GlancesAPI()` in on-demand mode, since one
  read of each plugin is all it needs. Its templates get `gl` (this API) and
  a second, fetch-only object for the TUI look (coloured quicklook bars,
  titles, separators), as sketched in the mockups of 2026-09-26. Whether
  v4's three renamed field names get aliases in templates is still an open
  question from those mockups.
- **`glances.ipynb`** is rewritten against `api_v5` in the same push as the
  API. It is the most visible user of the API.

## 9. Shipping

Three commits:

1. **The core**: `glances/api_v5.py` (loop thread, on demand, background,
   `close`), `PluginView`, the helpers, `DEPENDS_ON` on `processlist` and
   `programlist`, and the tests.
2. **The shared view**: `McpPluginView` rebuilt on `PluginView`. No
   behaviour change; the MCP tests prove it.
3. **The docs**: `api_v5_doc.py`, the `make docs` line, the regenerated
   `docs/api/python.rst`, the notebook, the README snippets, and the
   architecture document's backlog row moved to shipped.

## 10. Open questions for the maintainer

None block commit 1.

1. **Keep v4's `gl.cpu.get_raw()`?** Some v4 scripts may call plugin
   methods on the returned object. `PluginView.raw` covers the need;
   aliasing `get_raw()` onto it would keep those scripts running for the
   price of one line. Proposal: no alias, one documented rename.
2. **Refresh in background mode.** It follows `[global] refresh` and the
   per-plugin `refresh` keys, as Glances does. Should `GlancesAPI` also
   take a `refresh=` argument, for a notebook that wants 1 s without a
   config file? Proposal: yes. It is the API's equivalent of `-t`, the one
   CLI input the v4 API honoured.
